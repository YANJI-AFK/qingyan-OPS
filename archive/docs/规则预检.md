## 关键结论
规则预检只覆盖排班场景，导航等其他意图不在规则预检里！

意图 走规则预检？ 说明 schedule_query （排班查询） ✅ 全部 4 个 API 高频、句式固定，正则稳定可靠 operate （排班操作） ✅ 仅 schedule_assign 句式固定"让X排X日X班" navigate （导航） ❌ 靠 _rule_based_navigate() 兜底（Ollama 挂掉时） query / summary / search / staff_query / query_monitor 等 ❌ 全部走 LLM

## 为什么只预检排班？
看代码注释（第 138 行）就明白了：
 "规则预检：匹配已知的排班查询/导航/操作关键词，直接走意图执行（绕过 LLM 避免误识别）"
设计逻辑是： 排班查询句式高度固定 （"今日值班"、"X月X日排班"），用正则识别比 LLM 更 快 （零延迟）且 零误识别 （不会有 LLM 幻觉），所以优先用规则截胡。

而 导航 虽然也高频，但表达方式灵活（"打开监控"、"去服务器页面"、"看下大盘"），正则难以全覆盖，所以放给了 LLM 处理，只留 _rule_based_navigate 做 Ollama 不可用时的兜底。

补充 ：规则预检即使命中，也直接调用 execute_action_fsm ，与 LLM 命中的执行路径 完全一致 ——只是跳过了"理解"这一步。
