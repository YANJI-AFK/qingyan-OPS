## 一、系统架构

### 1.1 整体架构

轻言OPS 采用前后端分离的 B/S 架构，后端 Flask 提供 RESTful API，前端 Vue 3 + Vite 构建 SPA 应用。核心能力全部离线运行，不依赖外部云服务。

### 1.3 全离线设计

系统的核心设计原则是"全离线运行"，所有 AI 能力均本地化部署：

- **LLM 推理**：Ollama 本地运行 `qwen3:8b`，无需联网
- **语音识别**：FunASR `paraformer-zh` 模型本地缓存，首次下载后完全离线
- **语音合成**：优先 sherpa-onnx VITS 神经网络（离线），降级 Windows SAPI（离线），edge-tts（在线可选）
- **数据库**：本地 SQL Server 实例，无需云数据库

## 二、核心算法流程

### 2.1 对话处理主流程

系统采用**意图解析 + 状态机执行**的双层架构处理用户对话：

```
用户输入 (文本/语音)
    │
    ▼
┌─────────────────┐
│  1. ASR 语音识别  │  ← 若有 audio_data，调用 FunASR 转文字
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  2. 状态机检查    │  ← 若在 AWAITING_CONFIRMATION，走确认分支
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  3. 规则预检      │  ← 排班查询/导航等高频场景正则匹配，绕过 LLM
└────────┬────────┘
         │ 未命中
         ▼
┌─────────────────┐
│  4. LLM 意图解析  │  ← 调用 Ollama qwen3:8b，输出严格 JSON
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  5. 意图执行引擎  │  ← 根据 intent 分发到对应处理分支
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  6. 返回结果      │  ← reply_text + action + need_confirmation
└─────────────────┘
```

### 2.2 LLM 意图解析算法

`ollama_service.py` 中的 `understand_intent()` 是整个系统的"决策大脑"，核心流程：

```
输入: user_input + context_str
    │
    ▼
1. 构建 System Prompt（含 {{CURRENT_DATE}} 占位符替换）
    │
    ▼
2. 拼接上下文（最近 8 轮对话 + last_entity 指代消解提示）
    │
    ▼
3. 调用 Ollama API (temperature=0.1, max_tokens=500)
    │
    ▼
4. JSON 解析（多层容错）
    ├── 直接 json.loads()
    ├── 去除 ```json``` 包裹
    ├── 栈法提取最外层 {}
    ├── 截断 JSON 补全（补缺失的 }）
    └── 正则兜底提取
    │
    ▼
5. intent 字段清洗（_clean_intent: 处理管道符、空格）
    │
    ▼
6. 降级重试：若带上下文失败，无上下文重试一次
    │
    ▼
输出: {"intent": "...", "api": "...", "params": {...}}
```

**11 类意图支持**：

| intent | 说明 | 触发示例 |
|--------|------|---------|
| `navigate` | 页面跳转 | "打开监控"、"工单列表" |
| `query` | 数据查询 | "有多少未完成工单"、"查看工单5" |
| `query_monitor` | 监控查询 | "CPU 使用率"、"内存状态" |
| `staff_query` | 人员查询 | "有多少运维人员" |
| `schedule_query` | 排班查询 | "今日值班"、"7月23日排班" |
| `operate` | 修改操作 | "关闭工单5"、"让王强排早班" |
| `delete` | 删除操作 | "删除工单8" |
| `summary` | 趋势总结 | "总结本月趋势" |
| `search` | 多条件搜索 | "查数据库相关工单" |
| `greeting` | 问候 | "你好" |
| `unknown` | 无法识别 | 兜底 |

### 2.3 对话状态机 (FSM)

`chat_state.py` 实现 5 状态有限状态机，保障敏感操作的安全性：

```
                    ┌──────────────────────┐
                    │        IDLE          │ ← 初始状态 / 操作完成
                    └──────────┬───────────┘
                               │ 用户发起输入
                               ▼
                    ┌──────────────────────┐
                    │     PROCESSING       │ ← LLM 意图解析中
                    └──────────┬───────────┘
                               │
              ┌────────────────┼────────────────┐
              │ 普通查询       │ 敏感操作         │
              ▼                ▼                 │
   ┌──────────────────┐ ┌──────────────────────┐│
   │    REPLYING      │ │ AWAITING_CONFIRMATION││
   │  生成回复 → IDLE  │ │ 等待用户确认(30s超时)  ││
   └──────────────────┘ └──────────┬───────────┘│
                                   │ 确认         │ 取消/超时
                                   ▼              ▼
                        ┌──────────────────┐ ┌───┴───┐
                        │    EXECUTING     │ │ IDLE  │
                        │ 执行DB写操作→IDLE │ └───────┘
                        └──────────────────┘
```

**状态转换规则**（`ALLOWED_TRANSITIONS`）：

```python
{
    "IDLE":                    {"PROCESSING"},
    "PROCESSING":              {"REPLYING", "AWAITING_CONFIRMATION", "IDLE"},
    "REPLYING":                {"IDLE"},
    "AWAITING_CONFIRMATION":   {"EXECUTING", "IDLE"},
    "EXECUTING":               {"IDLE"},
}
```

**关键特性**：
- **敏感操作拦截**：删除/指派/排班操作默认需二次确认，确认词支持中英文（"确认/是/好/yes/ok"等），取消词同理
- **30 秒超时**：进入 `AWAITING_CONFIRMATION` 后 30 秒未确认自动取消并释放资源
- **指代消解**：通过 `last_entity` 追踪上轮实体，支持"其中有多少XX"等连续问答
- **卡死修复**：若检测到 `EXECUTING` 状态未正常回到 `IDLE`，强制复位

### 2.4 双重意图解析策略

系统采用**规则预检 + LLM 解析**的双重策略：

1. **规则预检（正则匹配）**：高频场景（排班查询/导航/排班操作）先用正则匹配，命中则直接跳过 LLM，降低延迟和避免误识别
2. **LLM 解析**：复杂意图交给 Ollama 处理，失败时自动降级重试（无上下文重试一次）
3. **规则降级**：`_rule_based_navigate()` 作为 Ollama 不可用时的兜底方案，覆盖日期+序号工单查询、导航、基本操作等

### 2.6 VAD 持续聆听算法

前端 `App.vue` 中实现了基于 Web Audio API 的 VAD（Voice Activity Detection）算法：

```
1. 获取麦克风 MediaStream
2. 创建 AudioContext + AnalyserNode
3. 每 50ms 采样一次 (VAD_POLL_MS)
4. 计算当前音量 = 频域数据 RMS
5. 动态噪声基线校准:
   - 每 60 帧 (3s) 持续静音时更新 noiseFloor
6. 语音判定: 当前音量 > noiseFloor × VAD_SENSITIVITY (2.5)
7. 状态机:
   idle → speaking (语音帧 > SPEECH_MIN_FRAMES)
   speaking → processing (静音帧 > SILENCE_MAX, 1.8s)
   processing → idle (ASR 完成)
8. 最短录音时长: 800ms (过滤瞬时噪声)
```

### 3.3 数据库连接池设计

`db_service.py` 实现了基于 `queue.Queue` 的连接池：

```
连接池配置:
  POOL_SIZE = 8          # 固定 8 个连接
  POOL_TIMEOUT = 5       # 获取连接超时 5 秒
  RETRY_COUNT = 3        # 失败重试 3 次
  RETRY_DELAY = 0.5      # 重试间隔 0.5 秒

连接生命周期:
  1. 应用启动 → _init_pool() 预创建 8 个连接
  2. 请求到来 → get_connection() 从池中借用
     - 同一请求内复用 (thread-local)
     - 连接失效时自动重建
  3. 请求结束 → Flask @teardown_request 自动归还
     - 有效连接放回池中
     - 失效连接关闭并补充新连接
  4. 应用退出 → close_all() 关闭所有连接
```

## 四、后端模块详解

### 4.1 app.py — Flask 主入口

**文件**：`backend/app.py` | **行数**：~1423

核心职责：
- **路由注册**：30+ 个 API 端点，涵盖对话/语音/工单/人员/排班/监控/配置
- **意图执行引擎**：`execute_action_fsm()` 函数，根据 LLM 解析的 intent 分发到 11 类处理分支
- **二次确认处理**：`_handle_confirmation_fsm()` 处理确认/取消/超时三种场景
- **环境检查**：启动时强制验证 venv 激活 + ffmpeg PATH
- **状态管理**：全局 `ChatState` 实例，Flask `@teardown_request` 自动归还数据库连接

**核心函数**：

| 函数 | 职责 |
|------|------|
| `chat()` | 对话主入口，状态机驱动 |
| `execute_action_fsm()` | 意图分发执行引擎 |
| `_handle_confirmation_fsm()` | 二次确认处理 |
| `_do_execute()` | 实际执行数据库写操作 |
| `transcribe()` | 语音转写接口 |

### 4.2 chat_state.py — 对话状态机

**文件**：`backend/chat_state.py` | **行数**：~204

核心类：

- **`ChatContext`**：封装对话上下文，包含：
  - `history` (最近 20 轮对话)
  - `pending_operation` (待确认操作)
  - `pending_operation_ts` (进入待确认的时间戳)
  - `last_entity` (上轮实体，用于指代消解)
  - `to_prompt_context()` 方法：将上下文转为 LLM 可读的 Prompt 文本

- **`ChatState`**：状态机主类，包含：
  - `transition(new_state)` 带合法性校验
  - `await_confirmation()` 进入待确认 + 记录时间戳
  - `handle_confirmation_input()` 中英文确认/取消词匹配
  - `is_pending_expired()` 30 秒超时检测

### 4.3 ollama_service.py — LLM 服务

**文件**：`backend/ollama_service.py` | **行数**：~706

核心函数：

| 函数 | 职责 |
|------|------|
| `understand_intent()` | 意图解析主函数，含降级重试 |
| `_parse_llm_json()` | JSON 多层容错解析（栈法+补全+正则） |
| `summarize_data()` | 数据润色（直出模式 + LLM 兜底） |
| `polish_search_result()` | 搜索结果润色（硬编码模板 + LLM） |
| `summarize_report()` | 趋势报告总结（代码拼基础数据 + LLM 分析趋势） |

| `call_ollama_raw()` | Ollama API 原始调用（3 次重试） |

**Prompt 设计**（三层架构）：

1. **`SYSTEM_PROMPT`**（~113 行）：意图解析的 System Prompt，包含 11 类意图的完整示例、中文数字转换规则、上下文连续问答规则、时间计算规则

### 4.4 asr_service.py — 语音识别服务

**文件**：`backend/asr_service.py` | **行数**：~154

核心特性：

## 八、安全与容错机制

### 8.1 二次确认机制

所有敏感操作（删除工单、指派工单、修改状态、排班分配）默认要求二次确认：

- 进入 `AWAITING_CONFIRMATION` 状态，等待用户明确说"确认"或"取消"
- 30 秒超时自动取消，释放资源
- 可通过系统配置页关闭特定操作的二次确认（`confirm_delete` / `confirm_assign` / `confirm_schedule`）

### 8.2 容错与降级

| 场景 | 策略 |
|------|------|
| Ollama 不可用 | 规则降级 `_rule_based_navigate()` 兜底 |
| LLM 返回空/格式错误 | 无上下文重试一次 |
| JSON 截断 | 栈法提取 + 自动补全缺失的 `}` |
| edge-tts 在线失败 | 降级 sherpa-onnx → SAPI 离线兜底 |
| sherpa-onnx 模型缺失 | 降级 SAPI 系统语音 |
| 数据库连接失效 | 自动重建连接，最多重试 3 次 |
| 状态机卡死 | 检测到 EXECUTING 未正常退出时强制复位 |
| FunASR 导入慢 | 5 次重试，每次等 3 秒（应对 Windows Defender） |

### 8.3 数据一致性

- 工单删除限制：仅允许删除"未完成"状态的工单
- 工单历史记录：所有修改操作自动记录到 `ticket_history` 表
- 连接池管理：请求级连接借用，`@teardown_request` 自动归还，防止连接泄漏
- 数据库迁移：`init_database()` 使用 `IF NOT EXISTS` 进行增量迁移，兼容旧表结构
